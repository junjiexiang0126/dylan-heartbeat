# 给知微：朋友圈原生接口与六次唤醒对接

本文件是**待知微实现的对接约定**，不是已经生效的功能。按用户上传的分工文件，ChatGPT 负责 `ziwei_web`，不修改 Hermes 内部，不向 Hermes 提供 Web 数据库或写入凭据。Web 的完整实现位于本 PR，保留 Face ID 与此前聊天修复。

## 已确定的体验

- 页签保留“朋友圈”，仍在聊天旁边；两个人可发布、点赞、评论，可删除，不可修改。
- 用户最多九张图片或纯文字，知微先发纯文字；未来可引用已存在的 Web 图片标识。
- 用户动态和评论保存到 Web 自己的数据库；不会自动转成原生长期记忆。知微可以自主选择记入自己的日记。
- 用户发布/评论后，Web 立即落一个后台任务，不等页面再打开。请求原文与当前动态的图片进入单独的 `*-moments` 会话。Web 不假造模型回复。
- 动态回复展示延迟 10–20 分钟，评论回复展示延迟 3–8 分钟。Web 在用户动作发生时选定并持久化 `due_at`；实际回复未生成时绝不提前虚构。
- 自主动态可直接展示。回复只允许每个触发编号一条；删除后保留墓碑，后续同步不会复活。

## 知微负责的两个能力

1. 注册 `ziwei_moment`，对 API 与 Cron 的**实际解析后的工具集**都可见。复用 `ziwei_status` 的修复，测试静态工具集与缓存，不仅检查注册表。原子追加原生自己的 `workspace/web-moments.json`，跨进程文件锁、原子替换并 fsync；写失败返回明确错误。
2. 安装只读 `GET /ziwei/web/moments`，沿用已有原生鉴权。Web 使用原有后端凭据读取；不增加 Web 写接口给 Hermes，不允许它直接写 Web 的业务库。

### 记录与追加扩展

保留原约定 `post`、`reply` 字段；增加点赞与撤回事件，才能完成用户这轮要求的双向互动：

| kind | 必要字段 | 规则 |
|---|---|---|
| post | id, author=ziwei, at, text, images=[] | text 1–2000 字；id UUID；at 必须带时区 |
| reply | 同上，加 reply_to | 对用户动态/评论回复；Web 检查目标确实存在并关联原动态 |
| like / unlike | id, author=ziwei, at, target_id | 目标动态 UUID；text 可空；表示本人点赞/取消 |
| delete | id, author=ziwei, at, target_id | 只能撤回本人动态/评论，绝不能删除用户内容 |

`context_note` 可保留在原生自己的记录里，**读路由应删除它**。Web 再次丢弃，既不存进自己的数据库，也不参与指纹，不传给浏览器。

Web 当前允许用户在自己的私人空间删除双方动态；原生工具只能撤回知微自己写的内容。任何已有 id 的正文更改都会被 Web 拒绝，不用同 id 覆盖。

### 用户内容的 parent 问题

用户动态只存在 Web，不能因为 `reply_to` 没出现在原生“知微出站记录”里而误判为不存在。当前运行的 Web 请求正文提供 `trigger_id`、`post_id`、用户原文及引用动态；将该已鉴权运行的目标上下文用于工具校验。Web 最终再次校验真实 parent。图片已经以受限的 image_url 内容传给本次运行；是否实际看懂仍需当前模型或原生视觉工具支持并实测，不能仅凭收到图片字段就宣称视觉验收成功。不要让模型通过任意路径读 Web 库，也不要新增写库凭据。

### 回复防重

Web 请求明确给出 `id` 和 `reply_to`，请让工具接受并幂等处理该 `id`，同一 reply_to 的回复需在原生锁内防重。Web 也有 `reply_to` 的唯一索引。重启/网络丢失接收响应后，Web 重用同一个持久化 run 幂等键与完全相同输入，不生成第二条任务。

### 读接口

```text
GET /ziwei/web/moments?since=<带时区 ISO8601>&limit=100
GET /ziwei/web/moments?cursor=<服务端游标>&limit=100
200 {"data":[...],"errors":[],"next_cursor":null,"has_more":false}
```

按 `(at, id)` 稳定升序，since 建议包含边界；Web 会重叠 1 ms 去重。超过一页时需要 `next_cursor`，否则相同时间戳或超过 100 条会漏记录。原生写失败/损坏返回 `errors` 或非 2xx，不能伪装成空 data。Web 看到原生 404 会显示“接口未接入”，不调用模型，待接口就绪后继续已有任务。

### 隔离与记忆

Web 只使用独立 `moments.sqlite` 与私有图片目录，不主动写 `MEMORY.md`/`USER.md`/原生记忆。

**提示词禁止 memory 并不是强制权限隔离。**请在原生侧给 `*-moments` 会话禁用 memory 写工具，并防止 file/terminal 等工具间接改写长期记忆，只保留经过限制的朋友圈工具和可选日记记录能力。否则不能把“不进长期记忆”作为已强制验收。

Hermes 本身可能保存该次 run 的会话/工具记录；这与自动提炼为长期记忆不同。若用户要求连 run 历史都不留，需要另行支持原生历史保留策略。不要通过删除现有历史或卷达成。

## 六次唤醒接入（由知微实施，尚未更改线上配置）

沿用现有 08/10/12/14/16/18（Asia/Bangkok）的六次**机会**及每日六次上限，不新建第二套定时器，不把六次机会变成六条动态。先核实真实 jobs 与执行回执，再声称已接入。

每次实际唤醒提供以下行动菜单：

```json
{
  "available_actions": ["contact_user", "rest", "self_directed_task", "publish_moment", "write_diary"],
  "choice": "由知微按当时实际情况自行选择；允许不发消息、不发动态",
  "moment_daily_post_limit": 2,
  "write_long_term_memory": false,
  "diary": "可自主选择记录少量体会，不复制整个朋友圈数据库"
}
```

- 联系用户：走已有主动消息能力。
- 休息：记录本次选择并结束，不伪造“已完成任务”。
- 自己做事：继续真实任务，保存结果与证据，沿用任务预算/并发限制。
- 发朋友圈：`ziwei_moment(kind=post)`，每日最多 2 条自主动态，按曼谷日期、在原生锁内校验。评论/点赞不计入自主动态数。
- 写日记：只写允许的日记目录，不修改用户指定由自己掌管的身份与长期记忆规则。

当前 `autonomy_gate.py` 在无活动任务且当日日记已存在时会跳过唤醒。如果希望即使空闲也拥有“发动态/联系/休息”的选择，需要**有条件**调整该门控；保留每日六次上限、连续失败暂停、证据检查和文件锁。`bootstrap.seed` 不覆盖持久化的审核脚本，只改镜像文件不会更新已运行脚本。应先备份并校验脚本再原子更新；不得重置机会计数或清空任何记忆。

## 两端联合验收

1. API 与 Cron 两入口实际能调用工具；原生真实发布返回成功，读接口有同 id，页面出现同 id。
2. 用户发文/评论后关掉页面，服务端仍有真实 run 和回复记录；记录用户 at、原生 at、Web scheduled_at，证实延迟分别落在范围内。
3. 同一触发并发两次、丢失接收响应、Web 重启后只有一条回复；已删除内容不复活。
4. 写失败能看到错误，不显示伪成功；context_note 在 Web API/数据库/DOM 都没有。
5. 六次机会里验证一次自愿发动态、一次 rest；不是定时必发。日记记录由知微自主决定；不得新增长期记忆。
6. 知微点赞/取消点赞/撤回本人动态，并验证拒绝删除用户内容。

当前自动化使用隔离夹具；不算以上真实联合验收。
