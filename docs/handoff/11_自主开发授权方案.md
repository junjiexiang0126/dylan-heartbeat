# 11 · 知微自主开发授权方案（GitHub App）

生成时间：2026-10-17
状态：**设计，未实施**。本节只写方案与风险，未创建任何 App、未改动分支保护、未接触任何密钥。

## 一、为什么不用 PAT

当前 `.env` 里那把 PAT 已经暴露两个硬伤：

| 现象 | 证据 |
|---|---|
| 不能改 workflow | `refusing to allow a Personal Access Token to create or update workflow ... without 'workflow' scope` |
| 不能触发/重跑 CI | `403 Resource not accessible by personal access token`（缺 `actions:write`） |

PAT 是**长期凭证 + 全仓权限**，一旦泄漏影响全部仓库，且权限无法按仓库收敛。GitHub App 的安装令牌**默认 1 小时过期**、**只对安装时选定的仓库生效**，更符合"最小权限 + 短期凭证"。

## 二、所需权限（只给这些）

安装范围：**Only select repositories → `junjiexiang0126/dylan-heartbeat`**（安装时选，不选 All repositories）。

### Repository permissions

| 权限 | 级别 | 用途 | 不给会怎样 |
|---|---|---|---|
| Contents | **Read & write** | 建分支、提交、改代码 | 只能读 |
| Pull requests | **Read & write** | 创建/更新 PR、评论 | 不能开 PR |
| Workflows | **Read & write** | 修改 `.github/workflows/*.yml` | 就是现在这个卡点 |
| Actions | **Read & write** | `workflow_dispatch` 触发、读日志、重跑 | 只能看不能跑 |
| Checks | Read | 读检查结果 | 状态判断要靠轮询 runs |
| Commit statuses | Read | 读状态 | 可选 |
| **Metadata** | Read（强制） | 基本信息 | — |

### 明确不授予

- **Administration**：不能改仓库设置、不能改分支保护、不能删仓库
- **Secrets**：**读不到任何 Actions Secrets**（关键隔离）
- **Environments**：不能改生产环境、不能批准环境部署
- **Deployments**：不授予写
- **Organization / Members / Webhooks / Packages**：全部 No access

## 三、创建与安装步骤（需要你在 GitHub 页面做，一次性）

1. 打开 https://github.com/settings/apps → **New GitHub App**
2. 填写：
   - GitHub App name：`ziwei-dev-agent`（可自定，全站唯一）
   - Homepage URL：`https://github.com/junjiexiang0126/dylan-heartbeat`
   - **Webhook：取消勾选 Active**（不需要回调）
3. Repository permissions 按上表逐项设置；其余保持 **No access**
4. "Where can this GitHub App be installed?" → **Only on this account**
5. **Create GitHub App** → 记下页面上的 **App ID**
6. 页面底部 **Generate a private key** → 下载 `.pem`（只显示一次）
7. 左侧 **Install App** → 选 `junjiexiang0126` → **Only select repositories** → 勾 `dylan-heartbeat` → Install
8. 安装完成后，浏览器地址栏 `/installations/<数字>` 里的数字即 **Installation ID**

### 凭证放在哪里（不要发到聊天窗口）

推荐：写进 Railway 的 `ziwei-hermes-test` 服务变量（我能从进程环境读到，不出现在对话与日志）：

- `GH_APP_INSTALLATION_ID` = 第 8 步的数字
- `GH_APP_PRIVATE_KEY_B64` = `base64 -w0 < 下载的.pem` 的结果

备选：把 `.pem` 放到 `/data/hermes_native/secrets/gh-app.pem`，权限 `600`，告诉我路径即可；`GH_APP_ID` 与 `GH_APP_INSTALLATION_ID` 同样写进 Railway 变量。**不要贴到聊天里。**

## 四、main 分支保护（请在 Settings → Branches 设置）

规则名 `protect-main`，作用于 `main`：

- ✅ Require a pull request before merging
  - Required approvals：**1**（这样 App 不能自己合自己的 PR）
  - ✅ Dismiss stale approvals when new commits are pushed
- ✅ Require status checks to pass：选 `Ziwei unified regression`、`Ziwei Web isolated tests`、`Work isolated checks`、`Official Hermes preparation`
- ✅ Require conversation resolution before merging
- ✅ Do not allow bypassing the above settings（对管理员同样生效）
- ✅ Restrict deletions
- ✅ Block force pushes

## 五、CI 与生产凭证隔离（第 7 条要求）

现状核查（只读、待执行项）：

1. **列出所有 workflow 是否引用 secrets**：`grep -rn "secrets\." .github/workflows/`
2. **区分触发面**：`pull_request` 触发的 job 不应拿到生产密钥；`push` 到 main 才部署。
3. **生产密钥改用 Environment secrets**：Settings → Environments → 新建 `production`，勾 **Required reviewers**，把部署用密钥放进去；workflow 里 `environment: production`。
4. **fork PR 策略**：Settings → Actions → General → Fork pull request workflows → **Require approval for all outside collaborators**。
5. **workflow 权限收紧**：Settings → Actions → General → Workflow permissions → **Read repository contents**（默认只读），各 workflow 内用 `permissions:` 显式声明所需。

这样即便开发分支被 App 改写，也拿不到生产密钥——**App 本身也没有 Secrets 读权限**，双保险。

## 六、风险说明（不隐瞒）

| 风险 | 说明 | 缓解 |
|---|---|---|
| App 可改 workflow → 可能外传信息 | Workflows 权限等于能改 CI 脚本 | ① 不给 Secrets 权限；② 生产密钥放 Environment 且需人工批准；③ 关键 workflow 变更走 PR 审核；④ 定期看 App 的 audit log |
| 私钥泄漏 | 拿到私钥 + App ID + Installation ID 可换安装令牌（1 小时） | 私钥只进 Railway 变量或 600 文件；不写仓库、不写聊天；每 90 天轮换 |
| 自我合并绕过审核 | 若允许 App 批准 PR 即可自审自合 | 分支保护要求 1 人批准且 App 不是批准者；`Do not allow bypassing` 开启 |
| 过度授权 | All repositories 安装 | 只选单仓库 |
| 令牌长期有效 | PAT 无过期 | 改用 App 安装令牌（1h） |

## 七、授权后的验收测试（在测试分支上做，不动 main）

| 能力 | 测试动作 | 判定 |
|---|---|---|
| 建分支 | 创建 `bot/acceptance-<date>` | 远端出现该分支 |
| 提交 | 提交一个仅改 README 的 commit | commit 可查 |
| 开 PR | 对该分支开 draft PR | PR 编号返回 |
| 改 workflow | 在测试分支改一行注释 | **推送成功**（当前 PAT 失败点） |
| 触发 CI | `workflow_dispatch` 一个工作流 | 返回 204 且出现 run |
| 读日志 | 拉取 run 日志 | 解压出 txt |
| 重跑 | `rerun-failed-jobs` | 新 run 出现 |
| 保护生效 | 尝试直接 push main | **被拒**（预期失败项，记录为通过） |

每项记录：时间、HTTP 状态、结果、证据链接。失败项原样保留，不美化。
