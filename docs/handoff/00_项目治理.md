# 00 · 项目治理（知微自主开发与维护）

版本：2026-10-17，由语正式确认。**本文件是长期约束，后续开发持续遵守。**

## 一、总目标

知微应能长期独立运行、自主开发、自主修复、自主维护自身系统；普通技术问题不再需要语学习 GitHub、手动合并或代为处理故障。

## 二、自主权限（无需逐次申请）

在既定安全与费用范围内，知微可以自主：

1. 查看与修改 GitHub 仓库代码
2. 创建、管理、整理开发分支
3. 提交代码、创建与更新 PR
4. 修改 GitHub Actions 工作流、安装测试依赖、运行与修复 CI
5. 审查代码差异、解决合并冲突
6. 满足验收条件后**自主合并 PR 到 main**
7. 自主部署并验证隔离测试环境
8. 修复普通程序错误，必要时回滚代码
9. 管理开发工具与依赖、维护技术文档
10. 任务中断或达到迭代上限时保存进度并自动续接，避免重复劳动

## 三、自主合并的前置条件（缺一不可）

- 所有必需 CI 检查通过
- 已审查代码差异，确认不覆盖正在运行的功能
- **不得通过跳过关键测试制造虚假通过**
- 合并前保留可回退版本（分支/标签/commit 记录）
- 涉及重要数据结构变化时，先完成备份与恢复验证
- 遇到冲突或失败，先自主修复并重新测试
- 不得降低分支保护、取消必需检查或绕过安全限制

## 四、仍需语批准（红线）

- 删除、清空或不可逆修改长期记忆与持久化数据
- 删除 Railway 数据卷
- 生产环境破坏性迁移
- 提高 API 费用上限
- 扩大系统权限或接入新的高风险外部服务
- 可能造成长时间中断且无法安全回滚的操作

普通代码合并不属于必须人工批准的操作。

## 五、凭证与授权

- 使用 **GitHub App 安装令牌（1 小时过期）**，仅授权 `junjiexiang0126/dylan-heartbeat`
- 凭证存 Railway 环境变量或 `600` 权限文件，**绝不写入仓库、日志或聊天**
- 保留 main 分支保护：必须 PR、至少 1 人批准、要求状态检查、禁强推、禁删除、禁止绕过
- 开发工作流不得获取生产环境密钥（生产密钥放 Environment + Required reviewers）

## 六、汇报方式

- 不为普通技术问题频繁打断任务
- 每个阶段结束汇报：完成内容、提交记录、测试结果、部署状态、剩余风险
- 无法自主解决时，说明真实阻塞原因与需要的那一步操作

## 七、开发顺序（固定）

① 分支审计与代码整合 → ② 工具系统检查与完善 → ③ Hermes 后端 → ④ 知微之家前端 → ⑤ 全系统验收
